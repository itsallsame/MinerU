# MinerU 4.0 业务平台：离线麒麟部署交接单

状态：开发侧交接文档，**不是现场部署通过证明**。2026-09-27 用户明确：Mac 用于开发测试；实际物理隔离的麒麟 x86_64＋NVIDIA 部署由另一团队实施。本仓库负责源码、业务代码、离线交付工具、操作说明和验收协议；实施团队负责目标制品准备、导入、构建、运行与现场证据回填。未填写的现场参数不得按默认值推断为已验证。

## 交付边界和系统构成

- 源码：`itsallsame/MinerU` fork 的干净 `master`，以交付时的**完整 Git SHA**为准，不以分支名或 `4.0.x` 浮动标签为准；不迁移旧 3.4/V1 代码或数据。
- 运行：两个代码镜像——`doclib-worker`（内部 Doclib、模型/GPU）和 `business-api`（业务 API、同源业务 Web、持久任务恢复线程）。`docker/compose.business.yaml` 使用一个内部网络；Doclib 不发布宿主端口。业务 API 是开放系统，没有登录、用户、角色或令牌授权；扩大宿主监听范围须由现场网络边界承担风险评估。
- 模型：完整权重在麒麟宿主**版本化独立目录**，由 worker 只读挂载；模型清单是单独文件。业务 API 不挂模型、无需 GPU。源码、Web 静态产物、wheelhouse、基础镜像、两个代码镜像、模型目录、运行数据与业务状态备份是不同制品。
- 更新：纯业务代码变更交付增量源码包及必要的 Web 包，重新构建受影响的代码镜像，不重传未变模型；纯兼容模型更新在新目录导入权重、生成新发布记录并重启 worker，不重建代码镜像。若上游接口、依赖或推理代码变化，必须作为联合更新重新验收，不能只换权重。
- 自有 Skill：`skills/business-documents/` 通过同一业务 API 工作，不直接使用官方 Skill、Doclib 内部端口或远程解析；Agent 不能自动越过人工确认。

## 建议执行顺序与硬停止点

1. 在联网的 Linux amd64 准备机，按[离线部署手册](offline-deployment.md)步骤 1–3 锁定基础镜像和依赖、按**精确模型提交**制备权重、构建 Web；从干净源码制作首次或增量 Git 包及独立 Web 包。通过批准介质交付，独立渠道传递各包摘要。不要在隔离机在线拉源码、依赖或模型。
2. 在隔离麒麟机先验包、核对源码完整 SHA 和模型来源锁；任何摘要、架构、ABI 或目录完整性不符即停止。按手册步骤 4–6 离线构建两个代码镜像、生成 `release.json` 和 `artifact-verification.json`。任一命令非零，不启动服务。
3. 现场预先创建**互不包含**的模型、模型清单、Doclib、共享原件、业务数据目录，核对权限；按步骤 7 运行 `scripts.verify_host_layout` 和 `docker compose config`。模型挂载为只读，业务镜像不挂模型。不得让 Compose 自动创建缺失的宿主目录。
4. 在物理断网状态启动服务，按步骤 8 运行 `scripts.verify_business_runtime`，生成新的 `runtime-preflight.json`。这仅证明所选制品、配置和基础 GPU/服务状态，不证明模型完成加载或质量达标。
5. 按步骤 9 使用[样本清单](2026-09-27-existing-samples.md)中的公共 PDF/图片做联通冒烟，然后用四类**有标注**真实样本做质量验收；Web 与自有 Skill 都走同一业务 API，核对机器候选未确认、人工复核后成果一致。做重启、模型缺失/损坏、GPU 不可用、物理断网、备份与回退演练。峰值显存和性能不列为本次联通验收门槛。任一阻断项失败，发布结论为未通过，不得用 Mac 或模拟测试替代。
6. 把本次 `release.json`、制品报告、运行态报告、脱敏样本指标报告、测试命令/退出码、目标环境信息、故障/回退记录、已知限制和双人复核结论保存在受控发布目录。报告链只证明字节关联，不是数字签名；现场仍须核对来源与物理隔离。

## 准备机与 U 盘交付说明（2026-10-11）

Mac 负责整理、测试并固定干净源码提交，构建与源码一致的前端 `dist`，生成源码包及独立 Web 包。用户提供的 Ubuntu 24.04 x86_64 准备机 `43.165.180.204` 已通过 SSH 只读检查：Docker 29.5.2、Compose v5.1.4、Python 3.12.3，可用磁盘约 42 GB；检查未显示 NVIDIA GPU。该机可准备 Linux amd64 依赖、基础/代码镜像与生产用模型权重，但不能代替麒麟目标机做 GPU 推理验收。它是有公网地址的准备机，不是物理隔离的最终运行机；模型下载必须在允许联网时完成，目标机始终不联网。正式制品须在独立新目录准备，不覆盖该 Ubuntu 机器已有文件。

U 盘建议按一次发布版本分目录保存：`source/`（源码包及 manifest）、`web/`（前端包及 manifest）、`images/`（基础镜像及 worker、业务 API 镜像的 `docker save` 文件）、`wheelhouse/`（Linux amd64 锁定依赖）、`models/`（Torch 小模型与完整 vLLM VLM 的版本化权重目录）、`model-manifest/`（模型清单）、`release/`（发布记录及独立交付的各 manifest SHA-256）、`instructions/`（本手册与交接单）。这些是不同制品；U 盘容量还需包含镜像、依赖与文件系统余量，不能只按模型大小选。GGUF 与 ONNX 为其他可选后端，不属于当前 Torch＋vLLM 生产部署的必需权重。

实施人员使用顺序：从可信渠道取得 U 盘包摘要并逐项核验；按本手册导入源码/Web、模型和 `docker load` 镜像（或用随包基础镜像和 wheelhouse 在目标机无网络重建）；运行 `scripts.verify_offline_release` 核对来源提交、镜像、前端、依赖和模型；准备互不重叠的宿主目录，配置本手册第 7 步的环境变量与只读模型挂载；执行 `docker compose -f docker/compose.business.yaml config`，再 `docker compose -f docker/compose.business.yaml up -d`；按第 8–9 步检查运行态并上传真实文件完成页面/API/Skill 联通测试。只拿两个代码镜像、Web 和模型而缺基础镜像身份、模型清单、发布记录或持久目录配置，不能按当前发布协议验收。不得把 U 盘直接作为运行中的模型或数据库目录；先核验并复制到麒麟宿主的版本化目录。

2026-10-11 按 Hugging Face 对当前 `main` 文件树的大小盘点：官方 Torch 小模型仓库约 895 MB，官方 ONNX 小模型仓库约 858 MB，官方完整 VLM 约 2.328 GB；另有当前 Mac llama.cpp 使用的第三方 GGUF 仓库约 1.240 GB。当前生产方案只需 Torch＋完整 VLM，权重约 3.223 GB（3.00 GiB）；三个官方仓库全取约 4.081 GB（3.80 GiB）；再加这套第三方 GGUF 约 5.322 GB（4.96 GiB）。这是权重文件大小，不含基础镜像、代码镜像、wheelhouse、传输副本或运行数据；正式下载须锁精确提交并以实际清单重新计算。
