# Deepdive：基于 MinerU 4.0 的离线业务文档平台

> 2026-09-23。当前是开发基线分析，不代表业务功能已经实现。开发仓库是 `itsallsame/MinerU` 的 `master`；不对旧 3.4/V1 系统做代码、接口或数据迁移。

后续确认：本产品是**无登录、无用户/角色/权限管理的开放系统**。下文方案比较中的权限假设已被用户明确撤销；以架构设计及阶段计划的开放 API 约束为准。物理隔离、业务端口内网可达范围和 Doclib 内部网络隔离仍是部署边界。

## 问题理解

目标是在 MinerU 4.0 源码之上建设一套供人和 Agent 使用的业务文档平台：支持公文、论文、研究报告、报纸与自定义类型的解析、字段提取、质量检查、证据定位、人工复核、确认和成果交付。前端与**我们自己的 Skill**共用业务接口，Skill 不直连官方 MinerU 原始解析入口。

Mac 只负责开发和功能验证。生产环境是完全物理隔离的银河麒麟 x86_64 + NVIDIA：无法在线安装依赖、拉镜像或下载模型。模型权重作为独立制品保存在宿主机持久目录；日常从 Mac 向生产环境只导入必要代码，不反复传权重。

本质问题不是“要几个镜像”，而是如何在**同一个产品和源码体系**里把文档能力、业务状态和交付制品的变化边界分清。官方 Dockerfile 构建时从包索引安装 MinerU 并下载模型，不能原样承担本项目的可复现离线交付。

## 探索与推翻

### 第一轮：只通过 V1 解析 API 接入

这种办法实现快，但仅使用上传、解析、下载结果；MinerU 4 的文档库、搜索、续读和定位器无法自然成为产品基础。官方 V1 parse job ID 不是持久业务任务 ID。用户已明确允许推倒旧原型，继续保持旧平台与 MinerU 的“解析工具式”关系没有价值。

### 第二轮：在官方镜像内直接叠加所有业务代码和模型

这能形成单镜像，但每次离线交付代码都可能携带大模型层；官方 Dockerfile 也未安装本地源码改动。即使 Docker 缓存减少重新下载，跨隔离区传输完整镜像仍无法满足“只传必要代码”。因此**代码和模型必须分开交付**，而镜像数量可以按资源隔离需要决定。

### 第三轮：同源扩展、双运行角色、外置模型

保留 MinerU 4 为基础，在 fork 中集中增加业务模块、前端和 Skill 接口。开放的 Web/API 处理模板、复核与成果；文档能力工作进程持有文档库、解析与 GPU 推理。它们可由同一源码产生一个或两个镜像，部署拆分不意味着产品拆分。模型和数据位于宿主机持久目录，不进入 Docker 构建上下文。

深入检查源码后，`mineru.doclib` 已公开 `DoclibClient`、`DoclibInterface` 和类型化请求/响应；应先验证该公开接口是否覆盖业务需求，而不是假定必须修改文档库内部。文档库有进程所有权锁，因此不能让多个进程无协调地同时写同一文档库目录。

## 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
| --- | --- | --- | --- |
| 旧式独立业务平台 + V1 parse API | 实现快、边界简单 | 用不上 4.0 文档库主能力，形成两套平台感 | 不选 |
| 官方单体镜像内叠加业务与模型 | 启动表面简单 | 源码改动未必入镜像，模型随每次跨区交付 | 不选 |
| MinerU fork 同源业务化 + 外置模型/数据 | 充分复用文档平台、支持离线增量交付 | 需严谨处理上游合并、开放 API 的网络边界和文档库所有权 | 选择 |

## 场景验证

1. **普通代码迭代**：Mac 修改字段规则和前端；通过批准介质传源码；麒麟用预置基础镜像和离线依赖构建受影响的代码镜像；模型目录与文档库数据保持不变。页面与自有 Skill 读取同一业务结果。可满足目标。
2. **官方模型升级**：联网准备环境按目标 Torch + vLLM 组合下载并校验；模型目录以独立版本包进入隔离区；与当前 MinerU 代码做真实样本回归，兼容才切换目录并重启推理。旧模型目录保留用于回退。不能只复制单个权重文件就宣称升级完成。
3. **官方 4.x 代码升级**：从官方上游合入确定版本，解决冲突并运行解析、文档库、业务闭环测试；离线重建受影响的代码镜像。原有模型默认不传输，但必须校验新代码与权重兼容。
4. **异常与反例**：若文档库只支持单实例，两个服务各自直接打开同一索引会破坏所有权边界；由一个文档工作进程独占，并通过内部接口或公开客户端访问。若 Skill 返回未复核字段却标记为最终结论，则违背业务需求；结果必须携带确认状态与证据。

## 高可信结论

- 开发必须在用户 fork 的 `master` 上进行；官方仓库作为只读上游，后续合入确定版本。不新增分支，不兼容旧系统。
- 正式 Dockerfile 应安装本地 fork 源码，禁用构建期模型下载；模型目录外置，并在离线运行时设为 `local` 源。
- 生产仅能离线运行；镜像、依赖、模型等初始制品在联网准备环境完成并通过批准流程导入，运行时禁止云端回退。
- 前端与自有 Skill 共用开放业务 API 的状态、操作记录和证据引用；MinerU 文档库负责内容索引，不另造全文索引。
- 两个运行角色是工程上的资源与所有权划分，不是两个独立产品；镜像可以按实际构建成本分为一个或两个。

## 尚需验证但不阻碍 Mac 开发

- 目标麒麟版本、NVIDIA 型号、驱动/CUDA 兼容性与可用显存；决定最终推理镜像基础层。
- 真实脱敏业务样本与人工标注；决定字段与证据准确率是否达标。
- DoclibClient 的上传/文档身份、检索、定位器、删除与重启语义；先做端到端原型，再决定是否改内部源码。
- 具体隔离区制品导入、恶意文件扫描、签名/哈希和备份制度；初版先提供可复现清单与断网测试。
- `LICENSE.md` 含商业使用门槛和对第三方在线服务标识条款；上线前由项目方核对适用义务。此处不是法律结论。

## 推荐起步阶段

先建立确定版本和离线构建基础：基于本地源码构建、模型目录外置、断网/模型缺失时快速失败、代码与模型版本清单。随后验证公开文档库接口，再定义全新业务契约及最小“上传—解析—证据—复核—确认”闭环。第一阶段不删除旧业务仓库里的用户文件；旧代码仅作为需求参考。

开发验证命令以用户确认的官方方式为准：uv 环境、pytest、Mac 本地解析冒烟；生产另做麒麟离线和 NVIDIA 真实样本验收。
