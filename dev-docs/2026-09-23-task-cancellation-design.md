# 任务取消：可承诺的语义与未完成工作

日期：2026-09-23；2026-09-24 增补。状态：从设计进入分层实现；是否完成 FE-016 仍以独立验收记录为准。

当前业务任务有 `uploaded/submitted/done/failed` 四态；重试复用保留的原文件。Doclib 公共客户端提供提交与读取解析批次，但没有按解析批次取消的契约。MinerU 的 V1 解析 Job 存在 DELETE 入口，但它不是当前 Doclib 任务的标识或队列，不能直接拿来取消业务任务。Doclib 的相同内容/档位解析可复用批次，多个业务文档可能共享底层工作。仅在前端隐藏任务，或把业务行改成“已取消”却宣称 GPU 工作停止，都是错误承诺。

目标语义应分开呈现：

1. `uploaded` 尚未交给 Doclib：业务库原子改为 `cancelled`，拒绝后续提交；保留原文与取消记录，避免把取消误做数据删除。
2. `submitted`：需要 Doclib 新增按批次的取消/引用关系契约。仅当批次尚在队列中且没有其他业务消费者时，才能确认实际跳过计算；共享批次不得中断其他文档。已经运行的计算若无法安全抢占，API 必须返回“仅停止本业务任务跟踪，底层计算可能继续”的明确状态，不得声称已停止 GPU。
3. 取消与完成并发时，以数据库状态转换为裁决；已完成的任务不能被事后伪装成已取消。业务 `refresh` 不能在取消生效后写入完成修订。重复取消需幂等，审计记录只记入口来源，不假装有个人身份。
4. 前端需要区分“取消业务任务”和“底层计算已停止”的确认文案；自有 Skill 只能走同一个业务 API。生产环境仍靠物理隔离限制开放 API 的可达范围。

在实现之前须先给 Doclib 增加队列取消能力及共享消费者约束，并补并发/共享批次/运行中/完成后取消测试。FE-016 保持未完成；现有 UI 不展示虚假的取消按钮。本设计不要求兼容旧 V1 代码或数据。

2026-09-24 前置不变量进展：业务 `refresh` 以前先单独插入完成修订、再单独把任务设为 `done`；两个操作间若出现竞争终态，可能留下“任务未完成但修订已可见”。现用 `BusinessStore.complete_task_with_revision` 在一个 SQLite `BEGIN IMMEDIATE` 事务内校验任务仍为 `submitted`、解析批次属于该任务且档位一致，插入/复用修订并标记 `done`。事务开始前任务若已进入终态，只返回终态而不创建修订。移除了原先可单独标记 `done` 的存储方法。这是将来取消与完成并发的必要条件，**不是**取消实现。

Doclib 当前 `request_parse` 按内容哈希、档位和页覆盖范围复用 `pending/parsing` 批次，`acquire_task` 直接从 `pending` 原子改为 `parsing`；队列表没有请求方/消费者引用，公开 `DoclibInterface` 也无批次取消方法。因此业务端即使知道自己创建的 parse ID，也无法证明后来没有 CLI、watch 或另一业务文档复用它。后续必须在 Doclib 请求/队列层记录消费者意图并提供原子释放/取消结果，区分“仅取消业务跟踪”“确认未执行”“已经运行/完成”；不能仅按业务数据库引用数决定是否删队列行。改造时须检查自动入库的请求方如何计数，并与 worker 领取批次使用同一数据库裁决。未经这一协议，不暴露“已停止计算”的按钮或 API。

2026-09-24 显式请求与自动入库分流：首次显式 `request_parse` 现在只做元数据入库，再按请求档位创建批次，不再由这条同步调用链先额外排一个默认 Flash。后台发现/入库仍排默认 Flash。这样 Standard 等显式请求不因本身先生成额外 Flash，也为后续“由谁请求这个批次”提供清晰起点；**不保证**后台 ingest worker 同时发现同一文件时不会抢先生成系统批次。现有请求流程中的 done/active 查询、复用和新建也还是分开的 DB 操作，不能拿当前 parse ID 列表直接做安全取消。

下一阶段的 Doclib 消费者感知协议按下列不变量实施，实施前仍只是设计：

1. 显式请求携带稳定、不可作为身份认证使用的消费意图键；业务任务用业务 task ID。Doclib 在同一写事务内重新检查活跃批次、创建缺失批次并为**每个等待的 parse ID**登记该意图，重试登记幂等。普通 CLI/SDK 未传键以及 watch/后台默认排队，都登记不可由业务释放的系统消费意图；旧库中没有登记的活跃批次也按受保护处理。不能仅靠 `created_parse_ids` 判断独占，后来的调用可能复用它。
2. 公开释放接口只接受该意图键与它实际持有的批次集合，在 Doclib 同一事务内释放登记。仅在没有其他有效消费者、批次仍为 `pending` 且 worker 尚未 `acquire_task` 时，以条件更新把它转为明确的“未执行/跳过”终态。若存在共享消费者，则只释放当前业务意图；若已 `parsing/done/failed`，不得返回“计算已停止”。每个批次分别返回事实结果，整任务只能按最弱结果描述。存储和公开状态、队列长度、缓存命中、复用规则须同步更新。
3. 业务库与 Doclib 是两个数据库，不承诺跨库原子事务。业务先持久化 `cancel_requested`，阻止完成修订写入；再调用 Doclib 释放；最后记录 `cancelled` 及每批次结果。崩溃/超时后按稳定意图键重试释放和核对，不把网络未知结果显示为“已停止”。`uploaded` 与正在 `submitting` 的竞争需用业务状态 CAS/可恢复提交意图裁决，防止取消刚生效后仍新排批次。
4. 验收矩阵必须覆盖：首次显式请求、自动/规则入库、同内容两个业务任务、CLI/Watch 与业务共享、多页多批次、请求/领取/释放并发、运行中与已完成、崩溃重启、重复释放和响应丢失。只有这组测试及实际 Doclib/业务/Web/Skill 联调通过，FE-016 才能标完成。

2026-09-24 消费者登记前置实现：Doclib schema v3 增加 `parse_consumers`，现存 `pending/parsing` 批次迁移时登记 `system:legacy` 受保护引用；后台新建批次在同一事务登记 `system:ingest`。显式请求的完成缓存检查、活跃批次复用、优先级提升和新批次创建现在使用 SQLite `BEGIN IMMEDIATE` 写事务，等待的每个批次在同一事务登记消费者键。业务任务以 `business:{task.id}` 登记，未带键的 CLI/SDK 请求登记受保护的 `system:request`；这个键仅标识工作意图，不代表用户身份或权限。重复请求复用相同批次时 `INSERT OR IGNORE` 保持登记幂等。

本次**仍未实现释放/取消**，也未解决跨库提交状态、响应丢失后重放、同路径后台入库竞争和强制重试的完整意图幂等性。未来释放接口必须先定义任务级意图墓碑与重放语义，避免已取消的键重新排队；不能因为有消费者表就认为任何批次可被取消。现阶段所有 UI/Skill 均不得展示“已停止底层计算”的说法。

补充审计点：后台发现同内容的第二路径时，现有 `_ingest_file` 会直接绑定既有 SHA 而不新建批次；这条早退路径尚未为它可能依赖的活跃批次登记系统引用。将来实现释放前，必须明确此类发现是否消费已有批次，并按语义登记或证明无须登记；对于无登记的未知活跃批次应继续保守视为不可取消。

2026-09-24 Doclib 层释放协议进展：同内容后台再发现（包括原路径早退）现在为既有 `pending/parsing` 批次补受保护的 `system:ingest` 引用；若它在业务独占批次已被跳过后才到达，则重新排入该跳过批次的档位/页范围并登记系统引用。schema v4 增加 `parse_intents` 持久墓碑、首次释放结果快照和每条消费者引用的释放事实。`POST /parses/release` 在 SQLite `BEGIN IMMEDIATE` 中先使意图失效，再逐批次释放引用。只有仍为 `pending`、未被 worker 领取、没有其他有效引用，且仅关联一条未被 watch 管理的活跃文件路径，才条件更新为 `skipped` 并回报确实跳过；否则回报 `shared`、`running`、`finished` 或保守的 `retained`。重复释放返回首次持久化的结果；即使批次之后被清理，快照仍可用于丢响应恢复。已释放意图无法再注册解析批次。消费者键不是身份或权限凭据；开放系统中的 Doclib 释放接口仅应在受网络隔离的内部服务范围内使用。

上述仅是 **Doclib 批次级协议**，还没有业务库的 `cancel_requested`/`cancelled` 状态机、跨库失败恢复、Web 文案或自有 Skill 入口，不能视为 FE-016 完成。当前自动补排沿用被跳过批次的档位/页范围；规则入库、多批次与跨进程并发的完整矩阵仍需继续验收。若产品要求「释放后绝不再计算」，它与后台新发现同一内容的需求冲突，必须按当时实际引用作逐批次事实反馈，不能给总括性的永久停止承诺。

2026-09-24 业务取消实现：全新业务库 schema 9 为任务加入 `submitting`、`cancel_requested`、`cancelled`，以及取消效果与 Doclib 原始释放结果快照。提交前先持久化 `submitting`，取消先在业务库持久化 `cancel_requested` 以阻止修订完成和提交状态的迟到写入，再用稳定 `business:{task.id}` 调用 Doclib 释放，最后持久化 `cancelled`。未知响应保持 `cancel_requested`；后续 GET 刷新或重复取消会重新调用幂等释放。崩溃于 `submitting` 时，GET 刷新可重交同一请求键。`uploaded` 在 CAS 后直接取消时记为 `not_submitted`；所有引用均实际跳过才记 `queued_skipped`；共享、运行中、已完成、保守保留或缺少可证明引用则为 `may_continue`。完成与取消以业务 SQLite 写事务先后裁决，不允许取消后补完成修订。业务 API、Web 与自有 Skill 使用同一取消入口，没有用户、登录、角色、权限管理；Agent 的 `--confirm-write` 只是使用约束，不是服务认证。

当前实现仍不宣称跨业务库/Doclib 原子事务、运行中模型抢占，且重复并发提交/失败后强制重试的消费意图世代化尚未完成验证。尤其 Doclib `force` 在前一批次瞬时完成后可能为同一业务键创建新批次；取消会释放同键全部已登记批次，但“同一次重试只创建一个批次”的幂等保证仍需独立处理。schema 8 和更早的开发库不自动迁移，新服务只接受 schema 9；既有文件不会被隐式修改，部署前须显式创建新库或使用匹配版本的备份。隔离麒麟/NVIDIA、四类真实标注样本与回退演练仍是独立验收门槛。

2026-09-24 提交世代协议：业务任务仍以 `business:{task.id}` 作为**工作意图键**，不引入账号、角色或权限。新业务库 schema 10 给每个任务持久化 `submission_attempt` 和 `submission_force`。初次提交为世代 1；同一次提交因响应丢失而重试时复用同一世代与 force 参数；只有已明确进入解析失败、页覆盖不足或无效批次等状态的重试才递增世代并启用 force。Doclib schema 5 在同一写事务中为 `(consumer_key, submission_attempt)` 保存请求指纹与第一次提交响应；同世代、同参数重放原响应，即使原批次已经结束也不再创建批次；参数冲突、跳号、已释放意图和已进入世代化后省略世代的请求均拒绝。释放墓碑继续覆盖该键的所有世代。业务提交成功/失败、解析轮询失败以及完成修订均按当前世代做条件更新，旧请求不能覆盖新提交。这解决本地开发测试可复现的 force 双排队与迟到轮询写入；仍不代表跨数据库原子事务或目标机验收。
