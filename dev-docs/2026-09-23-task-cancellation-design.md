# 任务取消：可承诺的语义与未完成工作

日期：2026-09-23。状态：设计边界，不是 FE-016 的实现或验收。

当前业务任务有 `uploaded/submitted/done/failed` 四态；重试复用保留的原文件。Doclib 公共客户端提供提交与读取解析批次，但没有按解析批次取消的契约。MinerU 的 V1 解析 Job 存在 DELETE 入口，但它不是当前 Doclib 任务的标识或队列，不能直接拿来取消业务任务。Doclib 的相同内容/档位解析可复用批次，多个业务文档可能共享底层工作。仅在前端隐藏任务，或把业务行改成“已取消”却宣称 GPU 工作停止，都是错误承诺。

目标语义应分开呈现：

1. `uploaded` 尚未交给 Doclib：业务库原子改为 `cancelled`，拒绝后续提交；保留原文与取消记录，避免把取消误做数据删除。
2. `submitted`：需要 Doclib 新增按批次的取消/引用关系契约。仅当批次尚在队列中且没有其他业务消费者时，才能确认实际跳过计算；共享批次不得中断其他文档。已经运行的计算若无法安全抢占，API 必须返回“仅停止本业务任务跟踪，底层计算可能继续”的明确状态，不得声称已停止 GPU。
3. 取消与完成并发时，以数据库状态转换为裁决；已完成的任务不能被事后伪装成已取消。业务 `refresh` 不能在取消生效后写入完成修订。重复取消需幂等，审计记录只记入口来源，不假装有个人身份。
4. 前端需要区分“取消业务任务”和“底层计算已停止”的确认文案；自有 Skill 只能走同一个业务 API。生产环境仍靠物理隔离限制开放 API 的可达范围。

在实现之前须先给 Doclib 增加队列取消能力及共享消费者约束，并补并发/共享批次/运行中/完成后取消测试。FE-016 保持未完成；现有 UI 不展示虚假的取消按钮。本设计不要求兼容旧 V1 代码或数据。

2026-09-24 前置不变量进展：业务 `refresh` 以前先单独插入完成修订、再单独把任务设为 `done`；两个操作间若出现竞争终态，可能留下“任务未完成但修订已可见”。现用 `BusinessStore.complete_task_with_revision` 在一个 SQLite `BEGIN IMMEDIATE` 事务内校验任务仍为 `submitted`、解析批次属于该任务且档位一致，插入/复用修订并标记 `done`。事务开始前任务若已进入终态，只返回终态而不创建修订。移除了原先可单独标记 `done` 的存储方法。这是将来取消与完成并发的必要条件，**不是**取消实现。

Doclib 当前 `request_parse` 按内容哈希、档位和页覆盖范围复用 `pending/parsing` 批次，`acquire_task` 直接从 `pending` 原子改为 `parsing`；队列表没有请求方/消费者引用，公开 `DoclibInterface` 也无批次取消方法。因此业务端即使知道自己创建的 parse ID，也无法证明后来没有 CLI、watch 或另一业务文档复用它。后续必须在 Doclib 请求/队列层记录消费者意图并提供原子释放/取消结果，区分“仅取消业务跟踪”“确认未执行”“已经运行/完成”；不能仅按业务数据库引用数决定是否删队列行。改造时须检查自动入库的请求方如何计数，并与 worker 领取批次使用同一数据库裁决。未经这一协议，不暴露“已停止计算”的按钮或 API。
