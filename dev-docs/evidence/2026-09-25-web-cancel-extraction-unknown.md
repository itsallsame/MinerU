# Web 取消与手动再提取的未知写入结果（2026-09-25）

## 发现

业务 Web 的任务重试已有“POST 结果不明 → 只读查任务”的防重复路径，但取消任务在 POST 5xx/断线后只提示错误，仍留下可再次发起 POST 的普通取消按钮。手动再提取在相同故障下也只显示通用错误，可让用户在未核对运行列表前再次创建提取运行。后者目前没有请求幂等键；即使读到某个运行，也不能证明它来自刚才的 POST。

## 修改

- 取消 POST 的断线、408/5xx、响应 JSON 损坏或身份不完整均视为未知结果。先 GET 同一任务；读回也失败时按钮变成仅只读的“核对取消状态”，列表刷新仍保留该状态。读回成功但任务未终结时，若用户要再次发送取消 POST，按钮显示上次结果未确认并要求明确确认；不自动重发。已处于 `cancel_requested` 的任务也只读核对，后台恢复线程负责继续协调 Doclib 释放。
- 手动再提取 POST 结果不明时，只读列出同一修订的运行；读回失败时只开放“核对提取运行”，不再 POST。读回成功后仍提示无法归因，若再次生成需用户确认可能出现重复运行。当前标签页在重选同一文档时保留该修订的未知标记。
- 两条路径对明确业务 4xx 保留错误提示；成功 POST 后的后续 GET 失败仍按已受理写入处理。没有增加用户、角色、登录或权限层，也没有改模型与业务 API。

## 验证与边界

新增两个 Playwright 浏览器回归，在旧实现上先因缺少只读核对提示而失败；修复后验证 503 + GET 503、列表刷新或重选文档、GET 恢复后不产生第二次 POST。前端单测 13 passed；最终离线 Web 构建为 8 个资源；完整 Chromium 回归 26 项通过；业务 API/服务定向回归 14 passed。

当前只在一个浏览器标签页的内存中保留取消和再提取的未知标记；刷新整个页面或重新启动浏览器后的跨会话恢复、真实网络故障、四类标注样本及隔离麒麟/NVIDIA 目标浏览器仍待验收。手动再提取缺少服务端幂等键，因此不能把“GET 运行列表”宣称为某次 POST 的确定结果。
