# 同一次上传的请求键与安全重放（2026-09-24）

业务语义：同内容的两次**主动**上传仍生成两个业务文档；只有同一 `Idempotency-Key`、同原文件名、同 SHA-256/大小、同请求档位和同模板代码的重放，才返回原文档与当前任务状态。请求键不是登录、用户身份或权限凭据。

实现边界：

- 业务 SQLite schema 为 8；`ingest_requests` 在文档与初始任务的同一个事务内记录请求键及上传意图。`BEGIN IMMEDIATE` 和键唯一约束裁决并发重放。已有键且意图不同返回 HTTP 409；键格式不合法返回 422。
- 重放需重新核对上传字节以防同键异文；这次临时发布的文件经哈希核对后删除，不再建立业务文档、任务或第二次 Doclib 提交。原任务若已变成 `submitted/done/failed`，返回其当前状态；失败任务仍走既有 task retry 入口，不在上传重放中偷偷重启解析。
- Web 为每个文件生成随机键，未知结果时只提供“使用同一请求键重试”，不自动重传；重试使用原 `File` 对象、档位和模板。自有 Skill 输出请求键，允许用户指示后用 `--request-key` 重放。无键或新键的上传仍是新的业务意图。
- 后续版本已加入同标签页恢复：发起 POST 前在 `sessionStorage` 保存请求键、文件名/大小、档位及模板代码，不保存文件字节。刷新后先通过开放 API `GET /api/business/upload-requests/{request_key}` 查询事务记录；查到则显示原文档/当前任务，404 只表示此刻尚未查到，不判定拒绝、不自动重传。用户必须重选同名同大小的原文件才可用原键重试，服务端仍以 SHA-256 和其余意图字段最终裁决；选错内容返回 409。浏览器存储不可用时保留当前页面的重试能力并明确提示勿刷新。自有 Skill 的只读 `upload-request KEY` 命令也使用这个开放接口，返回 `accepted` 或 `not_recorded_at_lookup`；后者不触发重传。Skill 调用方仍应保留输出的请求键。请求键不是认证凭据，跨标签页/会话未承诺自动恢复。
- 本项目明确不做旧业务数据迁移。schema 7 文件会被拒绝且原样保留；本版只初始化全新 schema 8 数据库。回退代码镜像不得直接挂载不兼容的 schema 8 数据库，需配套备份/恢复决策，不能把镜像切换说成完整回退。

验证：新增回归先证明旧 `DocumentWorkflow.submit` 不接受请求键；随后定向业务测试 36 passed，完整 Mac 业务测试 217 passed/1 skipped。覆盖同键重放、并发提交、跨 Store 实例重放、同键异内容/名称/模板冲突、HTTP 409/422、同内容新键仍创建独立文档、自有 Skill 对真实业务 API 重放；Ruff、Web 11 Node 测试、离线构建及 21 个 Chromium 回归通过。浏览器回归确认三份文件各用不同键，明确点击重试才用原键发第四次请求。

刷新恢复增量验证：开放 API 404/422/已记录返回契约及后续任务状态变化；浏览器合成回归验证两个断线请求在刷新后分别被核对为已入库和未查到，后者不自动重传，重选原文件后只用原键再次 POST。HTTP 503 也归为结果未知；页面实现用操作序号隔离过期核对响应，尚未单独模拟该并发时序。完整 Mac 业务回归 224 通过、1 跳过，Web 11 个 Node 测试、离线构建与 22 个 Chromium 回归通过。目标麒麟和真实网络中断仍未验收。

自有 Skill 的只读核对命令、5xx 未知结果处理与验证记录见 `dev-docs/evidence/2026-09-24-skill-upload-request-lookup.md`。

边界：上述是 Mac 合成/契约验证；未在隔离麒麟 x86_64 + NVIDIA 目标机、真实四类业务样本或故障注入的生产网络上验收。它保护同键重放；同标签页刷新能找回已保存的键，但不保证跨标签页/会话、浏览器存储不可用、不同客户端换键或人工主动重复上传的“恰好一次”。
