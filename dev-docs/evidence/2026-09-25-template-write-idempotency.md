# Template write request keys and unknown-result recovery

Before this change, a lost response to template **create**, **update**, or **disable** left Web unable to tell whether the write happened. A manual retry of update could create an unintended extra template version. Template validation errors also discarded the live draft on re-render.

Business SQLite schema 16 adds `template_requests` with a request key, action, template code, canonical write-payload SHA-256, result version, original enabled status, and timestamp. Each keyed write and its receipt commit in one transaction. A same-key/same-intent replay returns the original version without mutating again; a reused key with different intent returns 409. `GET /api/business/template-requests/{key}` reads the receipt without writing. The key is not an identity or authorization mechanism; the system remains open.

Web persists the key and full write intent in same-origin local storage **before** sending the request. If storage fails, it sends nothing. A network failure, 5xx, or malformed success response leaves the operation pending and blocks fresh template writes. After reload, Web offers read-only lookup; 404 does not claim rejection, and POST/PUT is never automatically retried. A user can explicitly confirm replay with the *same* key and body. Known validation errors retain the unsaved draft. This is client-side resilience, not a claim that a browser profile can never lose local storage.
