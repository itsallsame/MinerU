# 手动提取请求键与只读核对（2026-09-25）

## 问题与契约

原有手动再提取只复用同一修订的 `queued/running` 运行。一旦运行结束，丢失 POST 响应的客户端无法从运行列表证明哪一项属于自己的写入；再次 POST 会创建另一运行。新契约允许客户端在 `POST /api/business/revisions/{revision_id}/extractions` 传 `Idempotency-Key`（16–128 位 ASCII 字母、数字、下划线或短横线）。服务端把键、修订 ID 与运行 ID 写入同一 SQLite 事务：同键同修订重放返回原运行，包括已完成或失败运行；同键异修订返回 409。`GET /api/business/extraction-requests/{key}` 只读返回关联运行，未记录返回 404；404 只说明查询瞬间没有记录，不证明较早的未知 POST 一定失败。键不是身份、凭证或权限。

不带键的旧 POST 与自动首轮提取仍沿用“同修订活跃运行复用”规则。Web 和自有 Skill **目前尚未生成、保存或传递该键**，因此它们在结果不明时仍只能只读核对，不能安全归因或自动重发；客户端接入是下一阶段工作。

## 实现与破坏性边界

- 业务 SQLite schema 从 13 升到 14，新增 `extraction_requests` 表。新表与运行写入由 `BEGIN IMMEDIATE` 串行化，避免并发请求各建一次运行。
- 备份创建与校验现在要求 schema 14 且存在上传和提取请求键表；清单记录 `business_schema: 14`。旧 schema 13 会被明确拒绝，不自动迁移或删除旧数据。当前项目未上线且不要求 V1/旧开发数据库兼容；使用新空数据库前应自行保留需要的旧状态副本。
- 没有修改 MinerU 模型、模型权重、GPU 服务、登录、用户、角色或权限模型。
