# 两列 Markdown 表格字段候选（2026-09-24）

范围：P3 `BE-039` 的可追溯表格原型。MinerU 4 的本地 Doclib HTML Flash 可把原生两列表格输出为 Markdown 表格；业务提取过去只读“标签：值”行，漏掉这种显式字段行。

现在仅当历史修订的完整页文本含严格两列表头、Markdown 分隔行和后续数据行，且第一列与冻结模板字段标签完全一致时，才把第二列原文作为 `table_row` 候选。无分隔行、三列及以上、表头本身、标签不符、空值、超长值或未被完整读取的页不产生候选。同页同字段同值如同时来自普通标签和表格，保留先识别的 `label_rule`，避免数据库唯一约束导致整次提取失败；不同值继续形成需复核的冲突问题。表格候选绑定历史 parse ID 的页级冻结证据，**不声称能精确定位单元格**，也不会自动确认成果。Web 明确显示“表格字段行”，Skill 沿用同一业务 API 的 `method` 与证据。

为了使来源契约可持久化，业务 SQLite、离线停机备份校验同步升到 schema 13；旧 schema 12 及更早版本拒绝启动或作为新格式备份导入，不做隐式迁移，也不删除旧库。开发新库需用空目录初始化；目标机回退仍须配套相同版本的数据库备份、镜像和发布清单。模型权重与代码镜像的外置边界不变，系统仍没有登录、用户、角色或权限管理。

验证环境：Mac、本 fork 当前源码、Python 3.13、本地 Doclib HTML Flash/CPU。定向提取、数据库和离线备份 64 项通过；真实 Doclib HTML 两列表格联调通过，候选“办公室”及历史页冻结证据一致。最终完整业务回归为 336 通过、2 跳过、2 个第三方依赖警告；Web Node 13 项通过，8 个离线资产构建成功，离线 Chromium 24 项回归通过。Ruff lint、feature-list JSON 与 diff 检查通过。代码审查重点检查了历史修订身份、页截断、同页去重、表格拒绝条件、schema/备份一致性与候选未确认状态。

限制：仅覆盖结构清晰的两列 key/value Markdown 表格，不等于复杂、多列、跨页、图片或扫描表格抽取能力。尚无四类真实标注样本的字段准确率/证据命中率，也未在物理隔离的麒麟 x86_64+NVIDIA 上构建、加载模型或回滚。`BE-039`、P3/P6 继续未完成。
