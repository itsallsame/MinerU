# 真实 PDF 的业务修订与多批次解析验证（Mac）

日期：2026-09-23。范围：fork master 的 MinerU 4.0.6、业务 API/Doclib/Web。此证据不是麒麟/NVIDIA 生产验收。

## 发现与修正

- 仓库自带 `demo/pdfs/demo1.pdf` 为 13 页。Doclib 默认 PDF 页范围只覆盖 1–10；业务网关现在明确提交 `page_range=all`。
- Doclib 为 13 页产生两个批次（1–10、11–13）。业务原先按批次建修订，导致“最新修订”只有末 3 页。现在一个业务修订聚合无重叠的完成批次，任务必须覆盖全部 13 页；不完整或冲突批次失败并可强制重试。
- Doclib 的实际 short ID 不是 SHA-256 的固定前 12 位。修订 API 显式返回实际 short ID 和合并页范围，Web/Skill 使用同一业务 API，内部 parse ID 不对外公开。
- 历史读取、证据冻结、字段提取按 locator 页码选择批次，跨批次续读可继续到下一页；schema 7 存储该映射并拒绝旧原型库，未做迁移或兼容。

## 已执行验证

- 真实 Doclib 子进程 + 真实 FastAPI TestClient：上传 `demo1.pdf`，取回原文件，轮询至完成，只有一个业务修订且页范围 1–13，读取第 1/13 页、冻结并核验第 1 页证据、业务检索命中。相同字节再次上传为另一个业务文档，复用 Doclib 解析且仍各有一个完整修订。专用测试 2 通过。
- 全量 `tests/business`：107 通过；只有 FastAPI/Starlette 依赖弃用警告 2 条。
- Web 单元测试 7 通过；离线前端构建 7 个资产。Playwright 三条浏览器流程通过：业务检索/续读、Skill 证据深链、人工复核/确认。浏览器流程使用真实构建包与模拟业务记录；不是 13 页 PDF 的真实浏览器端到端。
- Ruff 检查业务代码及测试通过，`git diff --check` 通过。
