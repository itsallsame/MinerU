# Doclib 批次原子选择与消费者登记

日期：2026-09-24。源码基线：fork `master` 的 `d0a57151`。本轮属于 FE-016 的 Doclib 前置工作，不是取消功能交付。

实现：`DatabaseManager.write_transaction` 在跨进程有效的 SQLite `BEGIN IMMEDIATE` 内运行读改写。`request_parse` 的 done/active 查询、覆盖计算、优先级提升、新建及消费者登记在一个写事务内完成；业务提交传稳定的 `business:{task.id}`，无键的 CLI/SDK 请求登记受保护引用。后台新建批次与 `system:ingest` 登记同一事务；v3 迁移将旧活跃批次标记为受保护。消费者键不是用户身份或权限。模型、镜像与离线部署工况未改。

验证边界：跨独立数据库连接同时请求同一 PDF，断言只有一个 pending 批次且两项业务意图均登记；同键重试登记幂等；匿名请求增加受保护引用；显式请求与后台默认入库分别登记；迁移后的旧活跃批次受保护；一个请求同时复用旧批次和新建缺页批次时，两者均登记。消费者键拒绝空值、保留的 `system:` 前缀、空格和超长值，且在入库前失败。真实本地 Doclib 进程经公共 SDK/Unix socket 提交后，直接核对其 SQLite 登记。完整 Mac 业务套件 `247 passed, 1 skipped`；最终 Doclib 缓存与迁移套件 `225 passed`；最终官方单元套件 `2814 passed, 4 skipped`。修改过的核心文件 Ruff lint/format 与 `git diff --check` 通过；缓存语义大测试文件原有 13 项无关 lint 告警未批量重排。

真实本机 Doclib 进程联调还观察到后台扫描先发现新 HTML 的竞态：同一批次可同时具有 `system:ingest` 受保护引用和 `business:contract` 业务引用。这是预期共享语义，不能据显式请求的 `created_parse_ids` 推断业务独占；测试断言业务引用存在，并允许该后台引用。初始测试错误地假设业务独占而失败，改为共享断言后联调通过；这不是生产路径异常。

将并发用例扩展至“两请求同时首次发现同一路径”后，真实暴露出文件表普通 `INSERT` 的 `files.path` 唯一键竞争。现在使用 `INSERT OR IGNORE`，再按路径读取行，并按实际插入结果返回 `new/known`；若并发创建者尚未关联 watch ID，仍补上条件更新；后续解析入库依据文件行是否已有哈希决定是否需要执行。两种并发用例和 watch 关联回归均通过，避免只证明预先入库后的队列事务。此修复尚不能替代后台扫描与显式请求的完整并发矩阵。

未实现：消费者释放、队列跳过终态、跨业务库/Doclib 的取消恢复协议、并发后台入库与强制重试的完整幂等性。没有实际麒麟 x86_64/NVIDIA 和四类真实样本验收；不能据此宣称 FE-016 或整体 Goal 完成。

保守边界：后台发现同 SHA 的第二条路径会绑定既有文档并早退，目前不为已有活跃批次补登记系统引用。释放协议启用前必须审计/修复这一路径，且对任何没有消费者登记的活跃旧批次继续按受保护处理。
