# FE-033 B：派生结构版本与有限编辑 API

日期：2026-09-29。环境：本 fork `master`、macOS、项目 `.venv`。这是 B 的第二开发关口，不是 FE-033 的 Web/Skill 或最终质量验收。

## 交付与边界

- 新业务 SQLite schema 19 的 `structure_versions` 按业务解析修订 ID＋页码＋递增版本保存完整派生树、操作、来源、原因和时间。v0 为从历史 Doclib 原生结构即时构造的只读基线，首次成功操作追加 v1；不修改原始 Middle JSON、原件、冻结证据、字段决定或已确认成果。旧 schema 18 不隐式迁移，也不删除旧文件；尚未上线的原型需先归档、再以新空库初始化。
- 业务 API `GET .../structure/derived` 可取最新或指定旧版本，`POST .../structure/operations` 只接受受限操作：类型/标题级别、完整文字、拆分、相邻同级合并、同页移动/重排/改父子、插入和删除。客户端不能上传整棵树冒充机器结构。每次写入均校验预期页版本、历史修订与来源路径，陈旧提交 409。可选 `Idempotency-Key` 配合 `GET /api/business/structure-requests/{key}` 查询回执；同键同意图重放返回原版本，同键异意图 409。
- 原生节点 ID 对修订/页/原生路径稳定；人工新节点为随机 ID。来源记录保留原生路径、顶层 locator、原类型、预览和 bbox。派生文本独立保存为 `text_override`，不是原文证据；合并/拆分/移动不产生伪造的新原文坐标。页/树深/节点数/文字和请求大小受限，版本树与操作 JSON 的 SHA-256 不一致时拒读。这只能检出单侧损坏，不能对抗同时修改内容和哈希的数据库管理员。
- 离线状态备份脚本同步要求 schema 19 和 `structure_versions` 表，恢复验证同版数据库，不把旧 schema 18 当新库。模型和源文件部署方案不变。
