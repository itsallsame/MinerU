# 成果确认的复核快照前提

日期：2026-09-25。范围：开放业务 API 的成果确认、业务 Web；不增加用户、角色或权限系统。

问题：字段决定和问题处理是追加/更新式复核记录。旧页面可以在另一页面更改字段决定后继续点“确认”，原实现会把服务端最新决定写入成果，虽然旧页面从未看到它。请求键只解决响应未知和重试，不能表达“确认的是我看到的复核状态”。

实现：`POST /api/business/extractions/{run_id}/confirm` 现在必须带 `expected_decisions`（字段代码到最新决定 ID）及 `expected_issues`（问题 ID 到状态）。两张映射都允许为空，但不能省略。Web 在用户点击确认时，从当前已加载的决定和提取问题生成映射，并将其连同原请求键持久保存，确保未知结果的同键重放带同样内容。服务端在 `BEGIN IMMEDIATE` 中先检查同键同内容是否已有成果，再读取当前最新决定与全部问题，逐项比较；快照不同即 409，不写成果、审计或请求收据。已受理的同键同内容重放返回原成果，即便后来又有复核更改；同键变更快照则仍属异意图冲突。

Web 对明确的“Review snapshot changed” 409 删除未受理的待核对键、重新读取提取运行/决定/成果，并提示重新核对字段和问题后才能再次确认。未知响应（连接中断、超时、5xx、坏 JSON）仍走原键查询/人工同键重试流程，不把 404 当作未受理证明。服务端比较只涵盖决定 ID 与问题状态；它不是完整文档版本号，也不解决恶意调用方谎报快照、身份归因或其他工作流并发问题。

验证：存储用例覆盖旧决定、旧问题状态被拒绝、无收据、同键已确认成果在后续决定变化后可重放且异内容拒绝；API 用例覆盖缺少快照 422、旧页面 409、新快照 201；Chromium 合成用例在前一轮复核写入完成后模拟另一页面更改决定，检查旧快照被拒、页面刷新、无成果、再确认及未知响应同键恢复。真实多机并发压力、已标注业务原文及隔离麒麟 x86_64＋NVIDIA 机器仍未验收。
