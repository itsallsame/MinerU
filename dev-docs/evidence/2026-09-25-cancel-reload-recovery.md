# 业务取消未知结果的跨刷新恢复（2026-09-25）

## 缺口与处理

业务 Web 原先在取消 POST 响应丢失且任务 GET 也失败后，只在当前 JS 内存中保留“先核对”状态。整页刷新会丢失这项状态，重新显示普通取消按钮。新增 Playwright 断言在原实现上先超时失败，证明这个跨刷新缺口。

Web 现在发送取消 POST 前，把任务 ID 与 `probe` 待核对状态写入同源浏览器 `localStorage`；写不进去就不发送取消。POST 成功后清除标记；结果不明时保留 `probe`，刷新或重开同一浏览器资料后只提供“核对取消状态”。任务 GET 返回有效的同一任务且仍非终态时标为 `known`，再次取消仍须用户明确确认；GET 失败不重发 POST。任务变成 `cancelled/done` 后清除标记。GET 身份或状态不完整时不把它当成可靠核对。

这里没有新增取消幂等键或数据库 schema。服务端原有状态机已持久保存 `cancel_requested`，并用稳定的 `business:{task_id}` 释放意图协调 Doclib；客户端标记仅防止浏览器重载后误发第二次请求，不是取消成功的证明，也不是登录、身份或权限边界。更换浏览器资料、清除本地存储或另一终端访问不会携带这个 UI 标记，服务端真实任务状态仍须通过 GET 核查。

## 验证与剩余边界

离线 Web 构建 8 个资源；Web 单测 13 通过；完整 Chromium 浏览器回归 26 项通过。扩展的取消浏览器用例覆盖 POST 503 + GET 503、列表刷新、整页重载、只读 GET 恢复但任务尚未终结、用户拒绝再次取消、终态清除本地标记，以及浏览器拒绝写入标记时不发送 POST。服务端取消定向回归 6 通过（`tests/business/test_document_workflow.py` 和 `test_business_api.py` 的取消用例）。

浏览器故障均为合成响应；真实网络分区、隔离麒麟 x86_64＋NVIDIA 环境、四类脱敏标注原文尚未验收。P4 其余异步恢复与完整可访问性仍不能据此标通过。
