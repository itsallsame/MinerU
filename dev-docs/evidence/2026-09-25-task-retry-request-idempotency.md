# 任务重试请求键与跨刷新核对（2026-09-25）

## 发现与设计

旧的“重试解析” POST 在响应丢失后只能 GET 任务状态。即使 GET 当时看到 `failed`，也不能判断那是旧失败还是新重试很快又失败；再次 POST 可能形成额外提交。新增 `Idempotency-Key` 契约，将请求键、业务任务和提交意图写入同一 SQLite 事务。`POST /api/business/tasks/{task_id}/retry` 同键同任务重放只返回当前任务，不因任务再次失败而重新提交；同键异任务返回 409。`GET /api/business/task-retry-requests/{key}` 只读核对；404 仅表示查询瞬间未记录，不证明较早未知 POST 被拒。键不是用户身份或权限。

首次带键重试把可重试任务置为 `submitting` 并同时记录键；若进程随后退出，原有后台恢复扫描会推进这个已持久化的提交意图。无键内部调用保留既有提交世代和强制重试行为，但 Web/自有 Skill 的手动重试都传键。不同新键是新的明确重试请求；只有用户确认才能对未知请求用原键再次 POST。

## 客户端和离线状态

- Web 在 POST 前把 `{taskId, requestKey}` 保存到同源浏览器 `localStorage`；若不能保存，则不发送重试。响应不明只按键 GET；刷新/重开同一浏览器资料后仍可核对。读回 404 保留键，提供明确确认后的同键重试，不自动换键或重发。
- 自有 `business-documents` Skill 的 `retry` 输出请求键，未知结果只按键 GET；`task-retry-request KEY` 可在后续调用中只读核对。Agent 必须保留 JSON 中的键，跨 Agent 会话持久留存由调用方负责。
- 业务 SQLite schema 从 14 升到 15，备份创建/校验要求新请求键表并在清单写入 15。旧 schema 14 明确拒绝，不迁移或删除旧文件；新开发状态须使用空库。模型、模型权重、离线镜像拆分和无登录/无用户/无角色/无权限边界均未改变。

## 验证与剩余门槛

新增工作流测试在旧代码先因缺少 `request_key` 参数失败；实现后验证第一次强制重试很快失败，同键重放不再提交，新键可按既有提交世代继续恢复。另验证两个 SQLite 连接并发同键仅一个取得提交权、跨任务同键冲突、API 按键 GET、404/422/409，以及 schema 15 备份恢复和缺表拒绝。
