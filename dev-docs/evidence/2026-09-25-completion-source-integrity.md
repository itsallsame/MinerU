# 解析完成前保留原件核对（2026-09-25）

## 发现

原件提交 Doclib 时虽已在调用前后核对哈希，但任务处于 `submitted`、等待解析完成的期间，宿主机上的原件仍可能丢失或被改写。此前 `refresh` 在 Doclib 返回完成后可直接写入业务修订并排入自动字段提取，而原件下载接口已会对同一损坏原件返回 409。这会形成“业务结果已确认入库、原文却不可复查”的矛盾。

## 修改

上传存储新增统一的 `verified_source_path`：按业务记录的存储键找到普通文件，复核字节数与 SHA-256，并区分文件不可用与身份不匹配。原件 GET/HEAD 和 `submitted` 任务完成闸门共用该逻辑。Doclib 解析及 PDF 页覆盖检查通过后、业务修订事务前，`refresh` 再核对保留原件；损坏时以当前提交世代和 parse ID 作条件，将任务记为 `source_integrity_failed`；丢失时记为 `source_unavailable`。两种情况都不创建修订，也不会自动排队字段提取。旧世代轮询与取消仍受既有状态栅栏约束。

这属于误操作/意外损坏检测，不是防同 UID 或宿主机管理员并发篡改的机制；哈希核对与随后打开文件/提交数据库之间仍存在文件系统时序窗口。没有修改数据库 schema、模型文件、登录或权限设计。

## 验证

- 两个新增工作流负例先复现问题：解析完成前将原件改写为**相同字节数**的不同内容，或删除原件，旧实现仍把任务置为 `done`。
- 修复后负例检查对应错误码与“未生成修订”；原件 API 的 GET/HEAD 409 回归继续通过。
- 相关工作流、业务 API、上传存储测试：44 passed；Ruff 与 diff 检查通过。
- 完整 Mac 业务回归首次在受限沙箱内执行时，Doclib 测试进程绑定 Unix socket 被系统拒绝（`PermissionError: [Errno 1] Operation not permitted`），因此产生 28 个 fixture 错误，不能算业务测试失败或成功；在允许该本机测试权限后，**同一完整套件**为 365 passed、2 skipped、2 dependency warnings。

四类真实标注样本和隔离麒麟 x86_64＋NVIDIA 现场测试仍未取得；本地通过不替代这两项验收。
